# 일반 파일 일괄 다운로드 설계

## 1. 목적

브라우저 주소창에 URL을 하나씩 붙여 넣고 저장 대화상자를 반복하는 작업을, URL 목록 한 번 입력과 시작 버튼 한 번으로 대체한다. 기존 영상 다운로드, 영상 일괄 다운로드, 웹 재생 다운로드의 동작은 변경하지 않는다.

일반 파일 다운로드는 서버가 응답한 바이트를 변환 없이 그대로 저장한다. ZIP, PDF, 이미지, 문서, 실행 파일과 직접 MP4 URL을 같은 방식으로 처리한다. 직접 MP4를 이 기능으로 받으면 화질 선택, 병합, 인코딩과 FFmpeg 검사는 수행하지 않는다.

## 2. 기능 경계

### 지원 대상

- 공개 HTTP/HTTPS 직접 파일 URL
- 다른 HTTP/HTTPS 주소로 이동한 뒤 파일을 반환하는 URL
- 쿼리 문자열에 만료 토큰이 포함된 서명 URL
- `Content-Disposition: attachment`로 파일명을 제공하는 응답
- `Content-Length`가 없거나 파일명이 URL에 나타나지 않는 응답
- 서버가 범위 요청을 지원하는 파일의 중단 후 이어받기

### 초기 제외 대상

- 로그인이 필요한 브라우저 세션과 브라우저 쿠키 자동 가져오기
- JavaScript 실행이나 버튼 클릭 후에만 생성되는 다운로드
- `blob:`, `data:`, `file:` URL
- HTTP Basic 사용자명·비밀번호가 URL에 들어 있는 주소
- 사이트별 다운로드 버튼 자동 클릭
- FTP, BitTorrent와 클라우드 전용 공유 프로토콜
- 압축 해제, 설치 또는 다운로드한 실행 파일 자동 실행

브라우저에서만 성공하는 URL은 쿠키, Referer, 일회성 POST 요청이나 JavaScript가 필요한지 먼저 구분해야 한다. 초기 구현은 일반 GET 요청으로 파일이 반환되는 URL에 집중하고, 인증·브라우저 보조 기능은 별도 단계로 둔다.

## 3. 사용자 경험

기존 두 탭을 유지하고 세 번째 탭을 추가한다.

```text
단일 다운로드 | 영상 일괄 다운로드 | 파일 일괄 다운로드
```

파일 일괄 다운로드 화면:

```text
URL 목록 · 한 줄에 하나
[TXT 불러오기] [비우기]

저장 폴더  C:\Downloads                         [찾아보기]
동시 다운로드  [1 ▼]  [완료 항목 건너뛰기]

[실패 항목 다시 시도] [저장 폴더 열기] [파일 다운로드 시작]

전체 7/20 · 성공 6 · 실패 1 · 대기 13
┌────┬────────────────┬────────┬────────┬──────────┐
│ #  │ 파일명         │ 상태   │ 진행률 │ 속도     │
├────┼────────────────┼────────┼────────┼──────────┤
│ 1  │ report.pdf     │ 완료   │ 100%   │          │
│ 2  │ archive.zip    │ 받는 중│ 42%    │ 8.1 MiB/s│
└────┴────────────────┴────────┴────────┴──────────┘
```

- TXT 불러오기, 여러 줄 붙여넣기와 주석 줄을 지원한다.
- 입력 검증은 네트워크 요청 없이 수행한다. 서명 URL을 사전 검사하다 만료시키거나 같은 파일을 두 번 요청하지 않는다.
- 중복은 완전히 동일한 URL만 제거한다. 쿼리 값이 다르면 다른 URL로 취급한다.
- 기본 동시 다운로드 수는 1이다. 1~4 사이에서만 선택할 수 있게 하며, 서버 부하와 차단 가능성을 안내한다.
- 여러 작업을 동시에 받는 경우 단일 “현재 파일” 표시 대신 항목별 표를 사용한다.
- 전체 진행률은 파일 크기가 서로 다르거나 일부 크기를 알 수 없는 경우에도 일관되도록 항목 완료 비율의 평균으로 계산한다. 정확한 전체 바이트 진행률로 오해하지 않게 항목 수를 함께 표시한다.
- 완료 후 실패 항목만 메모리에서 다시 실행할 수 있다. 원본 URL을 별도 파일에 자동 저장하지 않는다.
- 초기 버전에는 실행 중인 전송의 별도 일시정지 버튼을 두지 않는다. 취소하면 `.part`를 보존하고 다시 시작할 때 이어받는 흐름을 사용한다.

## 4. 영상 기능과의 격리

| 입력과 명령 | 엔진 | 결과 |
| --- | --- | --- |
| YouTube·영상 페이지의 일반 다운로드 | 기존 yt-dlp 엔진 | 화질 선택, 병합, FFprobe |
| 기존 영상 일괄 다운로드 | 기존 `BatchService` | 영상별 처리와 이력 |
| 웹 재생으로 다운로드 | 기존 브라우저 캡처 엔진 | HLS/DASH 탐지 후 영상 저장 |
| 파일 일괄 다운로드 | 신규 HTTP 파일 엔진 | 응답 바이트를 원본 그대로 저장 |

파일 탭에서는 다음 자동 전환을 하지 않는다.

- HTML 페이지를 영상 페이지로 추측해 yt-dlp에 넘기기
- `.m3u8` 또는 `.mpd`를 완성 영상으로 병합하기
- 직접 MP4를 재인코딩하거나 컨테이너를 변경하기

HTML 응답을 받으면 기본적으로 실패 처리하고 “웹페이지가 반환되었습니다. 영상이면 영상 다운로드를 사용하세요.”라고 안내한다. 명시적인 HTML 파일 URL 또는 attachment 응답은 일반 파일로 허용할 수 있도록 콘텐츠 판정 규칙을 둔다.

## 5. 컴포넌트 설계

### `HttpFileEngine`

외부 `yt-dlp`나 FFmpeg를 사용하지 않는 전용 엔진이다. 표준 HTTPS 인증서 검증을 유지하고 GET 응답을 청크 단위로 파일에 기록한다.

초기 구현은 Python 표준 HTTP 라이브러리를 사용해 필수 의존성을 늘리지 않는다. 브라우저 인증, HTTP/2 또는 고급 프록시 요구가 실제 사례에서 확인될 때 네트워크 라이브러리 도입을 다시 판단한다.

책임:

- URL 검증과 HTTP/HTTPS 리다이렉트 처리
- 상태 코드 분류와 재시도 판단
- 응답 헤더 기반 파일명과 크기 결정
- `.part` 파일 기록, 이어받기와 원자적 완료 처리
- 다운로드 바이트, 전체 바이트, 속도와 ETA 보고
- 취소 시 활성 응답 닫기

영상용 `DownloadEngine`에 파일 전용 옵션을 추가하지 않는다. `FileTransferEngine` Protocol과 파일 전용 작업·결과 모델을 별도로 두어 yt-dlp 경로에 일반 HTTP 정책이 누출되지 않게 한다.

### `FileBatchService`

기존 `BatchService`의 URL 파싱, 요약 상태와 UI 표현 원칙은 재사용하지만 실행기는 별도로 둔다. 파일 전송은 이후 1~4개 동시 실행이 가능해야 하므로 현재의 단일 진행률 콜백을 그대로 공유하지 않는다.

파일 진행 이벤트에는 다음 값을 포함한다.

- 항목 인덱스와 안정적인 작업 ID
- 표시용 파일명
- 받은 바이트와 전체 바이트
- 퍼센트, 초당 속도와 ETA
- 상태: 대기, 연결, 받는 중, 재시도, 완료, 실패, 취소

`FileBatchThread`는 네트워크와 파일 I/O를 GUI 스레드 밖에서 실행하고 Qt 신호만 전달한다. 취소하면 실행 중 응답을 닫고 대기 작업을 미처리로 남긴다.

응답 본문은 짧은 간격으로 무응답 여부를 점검한다. 설정된 읽기 제한시간 안에서는
`응답 대기` 상태를 표시하고, 제한시간을 넘으면 `.part` 파일을 보존한 채 자동 재시도한다.
작은 네트워크 조각을 빠르게 받더라도 GUI 진행률 신호는 초당 최대 4회로 제한하여
화면 갱신이 다운로드 처리량을 떨어뜨리지 않게 한다.
완료 화면에서는 완료 행만 지우거나 입력·표·진행 상태 전체를 초기화할 수 있으며,
초기화는 이미 받은 파일과 완료 이력을 삭제하지 않는다.

### 설정과 저장소

영상 설정과 분리된 설정 섹션을 사용한다.

```toml
[file_download]
save_dir = "savedFiles"
history_file = "file_history.jsonl"
concurrency = 1
retries = 2
connect_timeout_seconds = 20
read_timeout_seconds = 30
resume_partial = true
```

- 영상의 `savedVideo`, `history.jsonl`, `failed_urls.txt`와 파일 다운로드 저장소를 공유하지 않는다.
- 파일 이력은 URL 원문이 아니라 SHA-256 지문, 최종 파일명, 크기, ETag와 완료 시각만 기록한다.
- 실패 URL은 앱이 열려 있는 동안 메모리에 보관한다. 사용자가 명시적으로 내보낼 때만 원문 URL을 TXT에 저장하며 서명 토큰이 포함될 수 있다고 경고한다.
- 서명 토큰이 달라진 두 URL은 같은 파일이라고 추측하지 않는다. 안전하지 않은 쿼리 제거 정규화 대신 정확한 입력 URL의 지문만 재개 키로 사용한다.

## 6. HTTP 처리 규칙

### 요청

- GET만 사용하며 사전 HEAD 요청은 하지 않는다.
- `Accept-Encoding: identity`를 요청해 압축된 전송 표현을 원본 파일로 잘못 저장하지 않는다.
- 운영체제 프록시와 기본 인증서 검증을 사용한다.
- 리다이렉트는 최대 횟수를 제한하고 최종 주소도 HTTP/HTTPS인지 다시 확인한다.
- 교차 호스트 리다이렉트에는 향후 추가될 인증 헤더를 전달하지 않는다.

### 상태 코드

- 200: 새 다운로드 또는 서버가 Range를 무시했으므로 처음부터 다시 기록
- 206: 검증된 이어받기 응답, 기존 `.part` 뒤에 기록
- 401: 인증 필요
- 403: 접근 거부 또는 서명 URL 만료 가능성 안내
- 404/410: 파일 없음 또는 만료
- 408/429/5xx: 재시도 가능, `Retry-After`가 있으면 제한 범위에서 존중
- 416: 로컬 크기와 서버 전체 크기가 같으면 완료 처리, 아니면 안전하게 재시작
- 204 또는 성공 응답이지만 본문이 없음: 빈 파일이 명시된 경우가 아니면 실패

재시도는 지수 대기와 작은 무작위 지연을 사용한다. 재시도 중에도 URL 전체와 응답 헤더의 인증정보를 로그에 남기지 않는다.

## 7. 파일명 결정과 충돌

파일명 우선순위:

1. `Content-Disposition`의 RFC 5987 `filename*`
2. `Content-Disposition`의 `filename`
3. 최종 리다이렉트 URL 경로의 마지막 요소
4. `Content-Type`에서 안전하게 추정한 확장자와 순번
5. `download-001.bin`

정리 규칙:

- 경로 요소를 제거하고 파일명만 사용
- Windows 금지 문자, 제어문자, 끝의 점과 공백 제거
- `CON`, `PRN`, `AUX`, `NUL`, `COM1` 같은 예약 이름 회피
- Unicode를 정규화하고 지나치게 긴 파일명 제한
- 저장 폴더를 포함한 Windows 전체 경로 길이도 확인하고 필요한 경우 본문 이름만 더 줄임
- 빈 이름은 안전한 기본 이름으로 교체
- 대소문자를 구분하지 않는 키로 같은 실행 안의 파일명을 예약해 동시 다운로드 충돌 방지
- 덮어쓰기는 기본 금지, `name (1).ext` 방식으로 충돌 회피
- 정리한 최종 경로가 선택한 저장 폴더 내부인지 다시 확인

서버가 제공한 확장자와 MIME이 다르면 자동으로 확장자를 바꾸지 않고 경고만 남긴다. 실행 파일 형식도 차단하지 않지만 자동 실행하거나 자동으로 열지 않는다.

## 8. 임시 파일과 이어받기

완성 파일과 같은 폴더에 고유한 `.part` 파일과 작은 메타데이터 파일을 둔다. 메타데이터에는 URL 지문, 예상 전체 크기, ETag, Last-Modified와 선택한 최종 파일명을 기록한다.

이어받기 순서:

1. `.part`와 메타데이터가 모두 일치하는지 확인한다.
2. 저장된 ETag 또는 Last-Modified를 `If-Range`와 함께 보내고 현재 크기부터 Range 요청한다.
3. 206과 `Content-Range` 시작 위치가 정확히 일치할 때만 append한다.
4. 200, 검증 실패 또는 리소스 변경이면 기존 부분 파일을 덮어쓰지 않고 별도 보관하거나 처음부터 다시 받을지 안내한다.
5. 완료 크기를 검증한 뒤 `.part`를 최종 파일로 원자적으로 변경한다.

취소와 일시적 네트워크 실패에는 `.part`를 유지한다. 영구 오류나 사용자가 “부분 파일 삭제”를 명시한 경우에만 제거한다.

## 9. 콘텐츠와 저장 공간 검증

- `Content-Length`가 있으면 남은 크기와 저장 장치 여유 공간을 다운로드 전에 비교한다.
- 동시 작업은 각 파일 크기를 개별 확인하는 데 그치지 않고 이미 예약한 전체 예상 바이트도 여유 공간 계산에 반영한다.
- 크기를 모르면 바이트와 속도만 표시하고 진행 막대는 불확정 상태로 둔다.
- 쓰기 중 디스크 공간 부족은 별도 오류로 분류하고 `.part`를 유지한다.
- 2xx라도 예상치 못한 `text/html` 로그인·오류 페이지이면 저장하지 않는다.
- `Content-Disposition: attachment`가 있거나 URL 확장자가 `.html`/`.htm`이면 HTML 파일을 허용한다.
- 서버 오류 문서의 일부 내용을 GUI에 그대로 노출하지 않는다.
- 선택 사항으로 최종 SHA-256을 계산할 수 있지만 서버가 제공한 기대 해시가 없으면 무결성 보증으로 표현하지 않는다.

## 10. 개인정보와 보안

- 화면과 일반 로그에는 URL의 호스트와 경로만 표시한다.
- 쿼리, 조각 식별자, Cookie, Authorization과 서명 값은 마스킹한다.
- URL 원문이 필요한 재요청은 작업 메모리에서만 유지한다.
- 리다이렉트 목적지는 로그에서 동일하게 마스킹한다.
- TLS 인증서 무시 옵션은 제공하지 않는다.
- 다운로드한 파일을 실행하거나 미리보기 앱으로 자동 전송하지 않는다.
- 저장 폴더 열기만 제공하고 파일 자동 열기는 제공하지 않는다.
- 장시간 전송 중 Windows 절전 방지는 사용자가 켤 수 있는 선택 사항으로 두고, 모든 종료 경로에서 즉시 해제한다.

## 11. 실패 안내

사용자가 다음 행동을 바로 결정할 수 있는 메시지를 제공한다.

| 상황 | 안내 |
| --- | --- |
| 401 | 로그인 세션이 필요한 URL입니다. 초기 파일 다운로드에서는 지원하지 않습니다. |
| 403 | 접근이 거부되었거나 URL이 만료되었습니다. 새 URL을 받아 다시 시도하세요. |
| HTML 응답 | 파일 대신 웹페이지가 반환되었습니다. 영상이면 영상 다운로드를 사용하세요. |
| Range 미지원 | 서버가 이어받기를 지원하지 않아 처음부터 다시 받습니다. |
| 디스크 부족 | 필요한 공간과 현재 사용 가능한 공간을 표시합니다. |
| 이름 충돌 | 새 이름으로 저장했음을 결과에 표시합니다. |
| 크기 불일치 | 부분 파일을 보존하고 완료로 기록하지 않습니다. |

## 12. 테스트 전략

외부 사이트에 의존하지 않는 로컬 HTTP 테스트 서버로 다음을 검증한다.

- 일반 파일과 빈 파일
- UTF-8 `filename*`, 한글 파일명과 경로 침범 파일명
- 동일 파일명 충돌과 동시 예약
- 상대·절대·교차 호스트 리다이렉트와 리다이렉트 순환
- Content-Length 있음/없음과 느린 스트림
- Range 206, Range 무시 200, 불일치 Content-Range와 416
- ETag 변경 후 안전한 재시작
- 401, 403, 404, 410, 429, 5xx와 Retry-After
- HTML 로그인 페이지 오인 방지
- 취소, 읽기 제한시간, 연결 끊김과 디스크 부족 모의
- URL 쿼리 토큰과 응답 헤더 비밀값 마스킹
- 전체/항목 진행률, 실패만 재시도와 앱 종료 후 부분 파일 보존

회귀 검증:

- 기존 영상 엔진 팩토리는 `HttpFileEngine`을 참조하지 않는다.
- 기존 단일·영상 일괄·웹 재생 작업자의 진입점과 설정을 변경하지 않는다.
- 일반 파일 작업을 시작하지 않으면 네트워크 파일 모듈이 실행되지 않는다.
- 기존 자동 테스트 전체가 그대로 통과한다.

## 13. 구현 순서

### 1단계: 파일 저장 기반

- 파일 전용 설정·모델·오류 분류
- 안전한 파일명 결정과 충돌 예약
- 스트리밍 GET, `.part`, 진행률, 취소와 원자적 완료
- 로컬 HTTP 서버 단위 테스트

### 2단계: 신뢰성

- 리다이렉트, 재시도, 상태 코드 안내
- Range/ETag 기반 이어받기
- HTML 오인 방지와 디스크 공간 검사
- URL·헤더 비밀값 마스킹

### 3단계: 일괄 서비스와 GUI

- 파일 전용 일괄 서비스와 Qt 작업자
- TXT 입력, 항목 표, 전체 진행률과 실패만 재시도
- 저장 폴더 열기, 부분 파일 유지·삭제 정책 안내
- 기본 동시 실행 1개, 설정 범위 1~4개

### 4단계: 동시 다운로드와 실제 검증

- 2~4개 작업의 파일명 예약, 진행 이벤트와 취소 경쟁 조건 검증
- 공개 직접 파일, 리다이렉트, 서명 URL 수동 검증
- Windows 패키지에서 장시간 실행과 절전·종료 동작 확인

### 후속 단계: 인증과 브라우저 보조

- 실제 사용 사례를 확보한 뒤 Referer, 사용자 선택 헤더 또는 브라우저 세션 지원 검토
- 기존 개인 브라우저 쿠키를 직접 읽는 방식은 보안·잠금·브라우저별 암호화 문제를 별도로 설계
- JavaScript로 생성되는 다운로드는 HTTP 파일 엔진에 억지로 결합하지 않고 전용 브라우저 보조 흐름으로 분리

## 14. 완료 기준

- URL 수십 개를 한 번 붙여 넣고 사용자 추가 조작 없이 순차 또는 제한된 동시 다운로드가 가능하다.
- 파일 종류와 관계없이 서버 응답을 변환하지 않고 저장한다.
- 실패 한 건이 나머지 파일 다운로드를 중단하지 않는다.
- 취소 후 부분 파일을 보존하고 지원 서버에서 이어받을 수 있다.
- 알 수 없는 전체 크기에서도 받은 바이트와 속도를 확인할 수 있다.
- HTML 오류 페이지를 정상 파일로 완료 처리하지 않는다.
- Windows 파일명과 경로 침범 입력을 안전하게 처리한다.
- URL 토큰과 인증정보가 화면·일반 로그·자동 실패 파일에 남지 않는다.
- 기존 영상 다운로드의 화질, FFmpeg, 웹 재생과 일괄 동작이 변하지 않는다.
